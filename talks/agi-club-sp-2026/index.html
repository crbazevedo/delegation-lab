I · O SISTEMA · O CONTRATO design by contract

Toda tarefa começa como um contrato escrito

tarefa: burst-guard
objetivo: rate limiting por tenant na API pública
pronto quando: 429 ao estourar · config por tenant · docs
pode ler: api/gateway/** · docs/limits.md
pode escrever: api/gateway/limits/**
autonomia: implementa + abre PR · merge segue humano
tamanho declarado: M
  • O  prompt é um ponteiro para este contrato.
  • Ele não muda enquanto a tarefa roda.
  • Áreas de escrita nunca se sobrepõem; agentes paralelos não colidem.
  • O tamanho é declarado antes de existir código.

Fixado de antemão: o que foi pedido, a quem, com quais limites.

I · O SISTEMA · O CRONOGRAMA directly-follows graph (DFG)

O trabalho forma um grafo de dependências

  • Uma onda: toda tarefa com insumos prontos, tudo de uma vez.
  • O paralelismo esbarra em escrita sobreposta e capacidade de revisão. Computação nunca limita.

O grafo de dependências limita a velocidade do trabalho.

I · O SISTEMA · O PLANEJADOR mdp fatorado · rddl

Escolher o que roda quando é um problema de decisão

// o mundo do planejador, em RDDL
stage(t) : {intake, build, ship, done};  // variáveis por tarefa
skill(t) : real;  dispatch(t), review(t) : action;
stage’(t) = if dispatch(t)  // despacho: uma aposta com probabilidades conhecidas
  then Discrete(done: skill(t), build: 1−skill(t)) else stage(t);
// atualização do lab: skill 0.78→0.70 ⇒ coverage 0.90→1.00
reward = Σt [ quality(t) − λ·review(t) ];  // a tese
  • O estado é um punhado de variáveis por tarefa e por agente: stage, tamanho declarado, habilidade estimada, revisão devida.
  • O próximo valor de cada variável depende de poucos pais. A recompensa soma por tarefa.
  • Um solver devolve uma política: para cada estado, a próxima ação, recomputada a cada onda.
  • Resultados fora da previsão alimentam a próxima onda por construção.

O grafo e os escopos de escrita são restrições duras. A política escolhe dentro delas.

MDPs fatorados: Boutilier et al. · RDDL: Sanner
I · O SISTEMA · O PLANEJADOR, FORMALMENTE rede de bayes dinâmica (2tbn)

O modelo de transição, desenhado como rede de Bayes

  • Duas fatias de tempo. Uma seta por dependência.
  • Um resultado revisado atualiza a skill; a skill reprecifica as tarefas abertas do agente.
  • Revisão devida não tem seta para skill: backlog não diz nada sobre qualidade.
  • Poucos pais por variável: tabelas pequenas, planejamento barato.
P(s′ | s, a) = Πi P(si′ | parents(si′), a)
  • Desenrolada para frente, planeja a onda. Condicionada no log, estima habilidade e deriva.

Um diagrama, duas direções: prevê para frente, aprende para trás.

I · O SISTEMA · O LOOP loop autonômico (MAPE-K)

O loop que roda sozinho

54+ h
execução mais longa, totalmente autônoma
  • Intake lê os roadmaps e cria tarefas candidatas que já nascem como contratos.
  • Admission controla cada candidata: dependências, áreas de escrita, capacidade e política. Veredictos: aceitar · reduzir · endurecer · adiar · rejeitar.

II · A TEORIA · USO 4: NO LIMITE

Algumas metas são impossíveis em qualquer orçamento

meta 90% · agente em 45% · detecta 80% · corrige 85%
lacuna a fechar:  0.90 − 0.45 = 0.45
cada revisão recupera:  0.55 × 0.80 × 0.85 = 0.374
0.45 ÷ 0.374 = 1.20 → revisar 120% das tarefas
✕ impossível: revisão sozinha não fecha a lacuna
meta de 80% → cobertura de 94%.

quando a matemática diz não

  • Encolher as tarefas
  • Testes & críticos melhores
  • Loop de reparo melhor
  • Baixar a meta, ou manter um humano

Todo pipeline tem um teto de qualidade: metas acima dele falham em qualquer orçamento.

Mais peças móveis → autonomia segura mais curta.

def gate(state) -> Command:
  verdict = ask(CRITIC, ...)
  if verdict.startswith("OK"):
    return Command(goto=END)
  if "DEFECT_SPEC" in verdict: 
    return Command(goto="spec", update={"feedback": [verdict]})
  return Command(goto="implement", update={"feedback": [verdict]})

Mesmos agentes, forma melhor: 46% → 88%

  • Menos ferramentas por agente: cada dobra nas escolhas taxa o buffer de autonomia (≈ 2% por bit).
  • Divida o mega-agente: pedidos menores sobem a habilidade crua. É o achado do tamanho.
  • Revise nas emendas: a passagem dá à olhada onde se segurar.

APÊNDICE · A5 · HISTÓRIA DE CAMPO

A execução que parou em silêncio

Uma execução autônoma longa pausou.
Sem crash. Sem erro.

O modelo vinha segurando a decisão de parar ou continuar, e escolheu parar, sem registrar nada.

  • Parar-ou-continuar saiu do modelo, para regras fixas sobre o log.
  • “Parar” não está no vocabulário do modelo; o fallback é trabalho ocioso útil.
  • Só o kill switch do operador para o loop.

O modelo nunca deve decidir quando parar.

APÊNDICE · OS ACOPLAMENTOS hooks · sidecars

Como o plano de controle toca um agente

hooks

Código em momentos fixos do loop do agente: antes de uma chamada de ferramenta, depois da saída. Pode bloquear: é código em vez de prompt.

adaptadores & sidecars

Um processo companheiro acoplado a um harness que não é seu. Ele traduz os eventos daquele harness para o log. Mesma ideia dos sidecars do Kubernetes.

skills

Conhecimento prático empacotado que o agente carrega sob demanda: procedimentos, checklists, regras de domínio.

playbooks

Sequências fixas de passos para tipos de tarefa conhecidos. O modelo improvisa só dentro de um passo.

O que precisa acontecer é código. O modelo preenche as lacunas de julgamento.

APÊNDICE · A6 · PULADO DE PROPÓSITO

O resto do plano de controle, em quatro linhas

blast radius

Ações ranqueadas de só-leitura → irreversível. Um workflow é tão arriscado quanto seu passo mais arriscado.

aprovações de uso único

Ações perigosas consomem uma aprovação emitida para aquele estado exato.

controle de admissão

Planos recebem uma de cinco respostas graduadas: aceitar · reduzir · endurecer · adiar · rejeitar.

confiança conquistada

A confiança é computada de resultados do log. A revisão nunca desliga; a taxa se move.

Um instinto em tudo: transformar julgamentos em comparações contra o log.

[3:40] Chamarei de modelo o componente que gera respostas. Agente é o modelo operando com contexto, memória e ferramentas. Harness é o ambiente que executa e restringe o agente. Acima disso, o plano de controle coordena contratos, agenda, políticas, avaliação e observabilidade. Contratos descem para os agentes; eventos e resultados sobem. Para quem constrói agentes, a consequência é importante: não é possível governar apenas pelo prompt ou pela resposta final. Precisamos observar o objeto completo que produz o resultado.
